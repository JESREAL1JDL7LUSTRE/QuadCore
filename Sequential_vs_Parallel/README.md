Sequential and parallel execution differ in how tasks are done and managed. Sequential algorithms are usually faster on small datasets because they don’t have extra work like creating processes or handling communication between them. Parallel execution can be helpful for bigger datasets, but it also adds extra work from splitting data, starting processes, and combining results. One of the main challenges was making sure all processes worked correctly together and that their results were properly merged. So, parallelism is useful for large problems, but for smaller ones it can be slower because the extra overhead is not worth it.

The performance behavior across dataset sizes differ depending on the size. In the 1,000 dataset, the parallel approaches are easily overtaken by the sequential approaches, as the dataset is small. However, in the 1,000,000 dataset, the parallel approaches are still  and in the 100,000 dataset, both methods are almost on par. One of the challenges during the implementation, aside from the confusions of sharing the same terminal, is the implementation of the parallel algorithm as the process will have to wait until all the workers are finished then merging the 4 processes. Additionally, creating 4 processes takes up time even before they have started to sort/search, costing more resources in the algorithm. The biggest issue comes from the overhead of spawning processes. Every time a search runs, it creates four separate OS processes, which already takes a few milliseconds before any actual searching even begins. On top of that, Python’s multiprocessing requires data to be serialized and copied into each process, so if you're working with something large, like a list with a million elements, you end up duplicating that data four times in memory just to perform the same search. Communication between processes also isn’t free, since results have to be passed back through queues, adding extra inter-process communication overhead. And because these processes don’t necessarily finish in order, the main program still has to do extra work at the end; comparing results and picking the earliest index to figure out which process actually found the target first. Parallelism is beneficial when the dataset is large, and also depends on how many “workers” you have to parallelize. In the case of the parallel linear search, the implementation of 4 chunks seems to be unnecessary as it will make 4 workers do the search, wait for all the workers and join, whereas in the linear search, it will not search the entire dataset as it will halt the search once it sees the target. In the test case examples, the dataset sizes are small, so sequential sort and search dominate, or are on par with their parallel counterparts. Hence, parallel approaches would only win if the dataset is very big and stored in shared memory.
